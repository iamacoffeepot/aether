# ADR-0160: Pumped Dispatch Home and the Desktop Window Actor

- **Status:** Accepted
- **Date:** 2026-07-22

## Context

The desktop chassis carries two main-thread bolt-ons, with different shapes but one root cause: the framework has no dispatch home whose drain runs on a caller's thread instead of the worker pool, and winit owns the main thread where window operations and GPU record/present must run.

**The window bolt-on has no actor at all.** `App` holds the Claim-stage `SettlingInbox` directly, decodes the three window kinds against hand-cached `KindId`s, calls `apply_window_mode` / `apply_window_title` / `apply_window_focus`, and mints replies itself — a hand-rolled mimicry of framework dispatch that has drifted in observable ways, all verified against current source. No `fold_handler_cost` call exists anywhere in the desktop crate, so `actor_cost aether.window` is permanently empty on desktop. The driver drain emits no `Received` / `Finished` hop events, so window traces are missing the brackets every other actor gets. No `capabilities()` registration runs, so the `CapabilityRegistry` has no `aether.window` entry on desktop, while `describe_handlers` — served by `aether-inventory`'s link-time fold — reports the *headless* companion's rows in the desktop binary. And `App::current_mode` is write-only; its documented reader (`platform_info`) was deleted in the issue 603 Phase 4 teardown and the doc comment still points at it.

**The render bolt-on is a real pooled actor with a shared-state seam.** `RenderCapability` dispatches on the pool, so its cost rows, trace hops, and registration are all correct — but its state is a bag of cross-thread handoffs to the driver: `RenderHandles` carries nine `Arc`'d accumulator fields with documented lock orderings and a `significant_drop_tightening` allowance guarding a TOCTOU window, `gpu: Arc<OnceLock<RenderGpu>>` is late-installed by the driver's `resumed`, and `CaptureBackend` is a cross-thread readback queue whose entries carry retained reply guards to the main thread. Every one of these exists because the handlers run on one thread and the frame recording runs on another.

The framework has since grown every piece a proper main-thread actor needs, and several were built for exactly this call site:

- `NativeBinding::from_ctx`'s rustdoc names "inside a `DriverCapability::boot` body" as its natural call site, and `NativeBinding::new` takes `spawner: Option<…>` with the inbox installed separately by design.
- The ADR-0155 §4 claim/start split (`claim_driver_mailbox` → `take_claimed_mailbox`) exists because the window mailbox needed reserving before any event loop runs.
- `MailboxClaim.wake_slot` (issue 1318) already delivers mail-arrival wakes into a parked event loop.
- `Dispatch<S>` being generic over state (issue 2311) means the `#[actor]`-generated dispatch table does not care who pumps it.
- Both the headless window handlers and the desktop `apply_*` methods already model "no window yet" as an `Err` reply, so a late-created window is an existing contract.
- `NativeActor::State: Send + 'static` is satisfiable for a state holding `Arc<winit::window::Window>` (winit 0.30's `Window` is `Send + Sync`).

The one missing primitive is the dispatch home itself.

## Decision

Introduce the pumped dispatch home in `aether-substrate`, migrate the window bolt-on onto it as the proving consumer, and name the render migration as the follow-on arc it unblocks. Three implementation slices for this ADR's scope, one named follow-up.

**1. `aether-substrate` grows `PumpedSlot<A>`, the externally-pumped dispatch home.** The body of `DispatcherSlot::dispatch_one` — `Received` / `Finished` trace brackets, `with_stamped` `Local<T>` resolution, framework arms then typed dispatch, cost fold, and the ADR-0106 single-settlement tail — is extracted into a free function `dispatch_envelope<A>` that both slots call, so there is exactly one dispatch semantics in the codebase. `PumpedSlot<A>` is a strict subset of `DispatcherSlot`: a single pump thread means no `SlotState` machine, no actor mutex, no seize path, and it is deliberately not `Send` — it lives and dies on the pumping thread. Its surface is `drain_available()` (drain every queued envelope; callable from any pump point on the owning thread) and `shutdown()` (residual drain, `unwire` under `with_stamped`, cost-row drop, registry finalize and monitor fan-out — the phases of the pooled Closed path).

`DriverCtx::boot_pumped_actor::<A>(config, params)` boots one from the Claim-stage reservation made under `A::NAMESPACE`: it claims the namespace `TypeId`, builds a `NativeBinding` via `from_ctx`, installs the claim's inbox re-lineaged onto the binding's disjoint reply-id space (`SettlingInbox::relineage`, additive — the claim's inbox was built without a lineage counter, and deferred replies must mint from the binding's space to preserve the issue 1695 disjoint-id invariant), registers `A::capabilities()`, seeds the cost table, and runs `init` / `wire` under `with_stamped` — the same sequence `NativeActorBoot` runs for pooled actors, so `describe` and `actor_cost` behave identically. It returns the slot plus the claim's `wake_slot` so the driver installs its own wake (desktop: an `EventLoopProxy` poke).

**2. `aether-window` grows `DesktopWindowCapability`, the desktop runtime of the `aether.window` mailbox**, behind a new `desktop` feature (`runtime` + optional winit), co-located with `HeadlessWindowCapability` per the ADR-0121/ADR-0122 reading that one crate owns every runtime of one mailbox. Its state carries the current mode and a `WindowCell` — a one-shot `Arc<OnceLock<Arc<winit::window::Window>>>` filled exactly once by the winit `resumed` handler. The handler bodies are today's `apply_*` methods; `resolve_fullscreen` moves here from the desktop chassis because it is window semantics. `Params` carries the cell and the initial mode (ADR-0156 §1 composer-supplied construction input; no new config section). `aether-inventory`'s `on_handlers` reply dedups field-identical rows, because two `#[actor]` blocks now legitimately share `NAMESPACE = "aether.window"` in one binary and the handler inventory is link-time global.

**3. `aether-chassis-desktop` swaps the driver onto the slot.** `App` drops the inbox, the cached kind ids, the `apply_*` / `drain_window_inbox` / `dispatch_window_envelope` methods, and the write-only `current_mode`; it gains `window_slot: PumpedSlot<DesktopWindowCapability>` and the `WindowCell`. `boot()` calls `boot_pumped_actor` and wires the wake slot to an `EventLoopProxy`; `resumed` fills the cell after creating the window; `about_to_wait` calls `drain_available()`; the run loop's exit calls `shutdown()` — the `unwire` the driver drain never had, landing before the passives' reverse-boot-order teardown since the driver boots last. The pump cadence and the wake mechanism stay chassis-owned; only the dispatch semantics becomes framework-owned. `try_framework_dispatch` and the `dispatch_*_tail_if_matching_free` re-exports retire with the drain. `consume_lifecycle_reply` stays: `aether.lifecycle.advance_reply` is a bespoke reply inbox, not a capability mailbox, and is out of scope here.

**4. The render migration is the named follow-up, with its constraint recorded now.** Pumping `RenderCapability` on the driver thread would collapse the entire `RenderHandles` mutex seam, the GPU `OnceLock`, and the `CaptureBackend` cross-thread machinery into plain state fields on a same-thread actor. But render cannot reuse the window's pump point: draw mail is emitted mid-frame as descendants of the `LifecycleAdvance` broadcast chain, and the driver *blocks* in `await_internal_signal` waiting for that chain to settle — settlement requires the render handlers to have dispatched, so a render slot pumped only at `about_to_wait` deadlocks the advance loop. The requirement is a pump point inside the settlement wait. `await_internal_signal` is a `recv_timeout` re-arm loop, so an interleaved drain (per-round pump hook, or a wake-aware select over the wake slot and the settlement signal) is an additive extension; `PumpedSlot`'s own surface needs nothing new — `drain_available()` is already callable from any pump point on the owning thread. The migration also has open design questions that earn their own ADR: how the driver invokes frame record / present on the pumped state (direct same-thread state access vs. an internal mail kind, which would give frame recording its own trace and cost brackets), and `SubstrateHarness` becoming a second pumping driver (it owns a GPU with no winit loop and reads `RenderHandles` directly today). This ADR decides the primitive with that consumer in view; the render ADR decides the migration.

The Claim-stage boot vocabulary (ADR-0155), the wake-slot mechanism (issue 1318), and `DriverCapability::claim` / `config_members` are unchanged; `--describe` output on a headless host is byte-identical.

## Consequences

- The four window drift items in Context are erased structurally rather than patched: cost rows, trace hops, capability registration, and `describe_handlers` accuracy all come from the shared `dispatch_envelope` body, which cannot drift from itself.
- A second dispatch home is permanent framework surface — every future reader of the scheduler story learns that actors drain on the pool except pumped ones. The shared `dispatch_envelope` keeps the semantics singular, and `PumpedSlot` is the strictly smaller sibling, but the branch exists from now on. The render follow-up is what the branch buys: without it, the largest shared-state seam in the codebase is unfixable.
- `aether-window` gains a feature-gated winit edge. Default features are unchanged, so headless and harness consumers pay nothing.
- Two identity types own one namespace, which is already true today (headless capability vs. the driver drain); this makes it two *actor* types. The chassis builder's double-claim rejection and the per-process `TypeId` namespace claim keep it sound. A follow-up worth its own issue, not done here: a neutral addressing-only identity so peers can use `ctx.actor::<…>()`-style sends to `aether.window`.
- The `WindowCell` is a shared-state seam inside an actor model. It is the honest encoding of winit owning window creation on its own schedule: one `OnceLock`, private to the desktop chassis boot. Mailing the handle to the actor instead would be the same sharing behind an extra hop. The render migration inherits the same pattern for the surface-bearing GPU bundle.
- Trace and cost shapes for `aether.window` change visibly: traces gain `Received` / `Finished` hops and cost rows appear where none existed. Tooling or tests pinned to the old shapes drift and must be swept before the swap lands.
- Boot-window mail: mail landing between the Claim-stage reservation and the event loop starting sits in the inbox with the wake firing into a not-yet-running loop. Safe on winit because the loop starts under `ControlFlow::Poll`, so the first `about_to_wait` drains regardless — but a pumped driver whose loop starts parked must drain once at pump start. The render follow-up's harness pumping is the concrete case.
- Handler-side sends from the pumping thread exercise the pool-side blob demux (`dispatch_envelope` flushes the binding's outbound; a production binding folds blobs through the pool `WakeSink`). The sink is thread-safe, so this is supported — but it is untrodden until a pumped handler sends rather than replies, and the slot's tests must cover one non-reply send. The render migration makes this path load-bearing (render handlers send to `aether.trace` and peers), so it must be solid before that arc starts.
- The Occluded + `ControlFlow::Wait` wake path (issue 1318's reason to exist) must be preserved through the swap: the wake still pokes a redraw, and the focus-while-occluded scenario stays the manual regression check.

## Alternatives considered

- **Status quo (keep the hand-rolled drain and the render seam).** Rejected: the window drift tax is already visible in four places and grows with every framework dispatch change, and the render seam's lock-ordering and TOCTOU obligations are permanent reviewer load.
- **Host `DesktopWindowCapability` in `aether-chassis-desktop` instead of `aether-window`.** Mechanism-symmetric but leaves the two runtimes of one mailbox in different crates, and the "this crate hosts the companion" apology in `aether-window`'s crate doc survives. Rejected in favor of co-location; this is the one reversible taste call, and it flips a single use path.
- **Run the window actor on the pool and marshal each operation to the main thread.** Rejected: it adds a cross-thread hop per operation, a second queue to reason about, and reintroduces the "who owns the reply" question the settlement machinery answers today only for dispatch homes. It is also exactly the shape the render seam already has, and that shape is the thing being retired.
- **Generalize `DispatcherSlot` with a pluggable executor instead of a second slot type.** Rejected: the pooled slot's `SlotState` CAS machine, seize path, and actor mutex exist only because multiple workers race to drain it; a pumped home needs none of that, and threading an executor abstraction through the hot path taxes every pooled actor for the rare pumped one.
- **Migrate render in this ADR's implementation arc.** Rejected for sequencing, not direction: the window swap proves the primitive on a low-frequency mailbox with no chain-participation constraint, while render adds the settlement-wait pump point, the record/present invocation surface, and harness pumping — each a real design decision. Landing the primitive first keeps every slice small and lets the render ADR build on a proven dispatch home.
