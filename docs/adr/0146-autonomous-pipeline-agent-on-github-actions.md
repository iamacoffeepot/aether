# ADR-0146: Autonomous Pipeline Agent on GitHub Actions

- **Status:** Proposed
- **Date:** 2026-07-11

## Context

The issue pipeline (/sketch → /scope → /approve → /implement → /land) runs today with a human driving every transition from a local Claude session. Two pressures motivate changing that. First, the post-green stretch of a PR's life is fragile: agents reply to review findings but do not resolve the threads, hold flags are asserted by agents rather than derived from anything, and a flag that should clear when its condition clears instead waits for someone to remember it. Prose instructions have proven to be the wrong carrier for multi-step obligations — agents drop them under context pressure. Second, the pipeline's throughput is bounded by one person's attention: work that is fully specified and gated sits idle between sessions.

The repository already proves the substrate this decision builds on: the Review and Dogfood workflows run subscription-authenticated Claude sessions on ephemeral RunsOn machines, with an owner-gated, least-privilege security posture, event-chained via `workflow_run`. What is missing is durable machine-readable state for the PR lifecycle, and an orchestration layer that advances issues without a human hand on every edge.

Constraints that shaped the decision: the repo is public, so any trigger path that can reach secrets must be gated on the sender, not on convention; GitHub Actions offers no long-lived orchestrator process, so nothing may depend on a waiter that outlives a job; and the owner's judgment must remain the authority over what enters implementation and what merges — automation may move work through gates the owner has opened, never open a gate itself.

## Decision

Adopt a six-part architecture, implemented across #3126–#3133.

**1. One flat phase ladder.** Issue lifecycle state is a single `phase:*` namespace: Backlog (no label) → `define` → `design` → `plan` → `ready` → `building` → `qa` → `findings` → `held` → Done (closed, no label), with `bounced` and `stalled` as parked states. There are no sub-states and no separate PR-state vocabulary; humans and agents read the same ladder. `phase:executing` is renamed `building`; `phase:refine` is decomposed into `qa`/`findings`/`held`. Every phase is a *resting* state — it names what should happen next, never what is happening now.

**2. A reconciler is the single writer of `building`→`held`.** A hosted workflow (no Claude) recomputes that stretch from observable facts — CI check-runs, open review threads (GraphQL), review/dogfood rollup presence — on four paths: `pull_request` events (the payload carries the PR; `synchronize` is the push-demotes edge), `workflow_run` completions of CI only (its runs are `pull_request`-triggered, so they resolve to the PR — Review and Dogfood runs anchor to `main` and cannot), a `workflow_dispatch` QA-completion hand-off that the Review and Dogfood post jobs poke with the exact PR number, and a scheduled recompute backstop that covers thread resolve/unresolve (which emit no Actions event) and any missed poke. Every firing recomputes from scratch, so a missed event self-heals on the next one; any push demotes `held`/`findings` back to `building`. When the rung-① GitHub App exists its webhook can forward a thread event as a dispatch poke, leaving the schedule a pure backstop. The governing principle: state that agents assert rots; state that machinery computes stays true. Under a computed gate, an agent forgetting a step is a liveness hiccup, never a lie.

**3. Liveness is computed, never stored.** A work claim *is* a live `agent-work` run with the deterministic `run-name: work-{task}-{ref}`; the dispatcher checks `gh run list`, and `concurrency: work-{task}-{ref}` makes the singleton per (task, ref) platform-enforced. No claim labels exist. A worker that dies never moved the state, so the next dispatch cycle re-dispatches it — crash recovery is the absence of a mechanism. Every work job's first step is a re-entrancy guard (already merged? branch exists? which label is present?), and its first visible act is a start-of-work comment carrying the run link.

**4. Dispatch is a wavefront with a computed barrier.** The tick (`agent-tick.yml`) dispatches a wave only when the board is quiescent — no live `agent-work` runs; completed runs re-trigger the tick via `workflow_run`, so waves chain at the natural pace of the work and cron is only the missed-event backstop. The dispatch set locks at wave start. `land` tasks bypass the barrier (minutes long, re-entrant, unblock downstream work). All rate control converges on one choke point: repo variables for wave width, minimum inter-wave gap, and wave budget — free-running operation is the governor opened wide, not a different mode. `AGENT_ENABLED` (repo variable, checked first) is the global kill switch; the `agent:dont-touch` label is the per-issue one — it blinds the dispatcher while the reconciler keeps the bookkeeping truthful, the agent may self-apply it when flailing, and only the owner removes it.

**5. The agent is a GitHub App with an isolated subscription, and questions park.** The agent acts as an installed GitHub App: per-job scoped tokens, a visibly distinct identity, and — decisively — App-created events trigger downstream workflows where `GITHUB_TOKEN`-created events do not, which the pipeline's event chaining requires. Claude auth uses a dedicated subscription token, pool-isolated from the QA chain's so neither can starve the other. Every trigger path that can reach a secret carries a job-level owner gate on the sender; the least-privilege split from the Review/Dogfood workflows (code-executing job read-only; write scopes only in a job that never runs branch code) is reused as-is. When a headless skill needs the owner, it asks and parks: a structured question comment, the `agent:awaiting-answer` label, session state to S3, exit 0 — the owner's reply re-dispatches the job, which resumes the session. A parked question holds no machine and blocks no wave.

**6. Autonomy is gated, and the gates ratchet by evidence.** Approval decomposes into a mechanical completeness check, a policy lookup, and taste — and only the first two automate. An in-repo policy file maps path globs to approval tiers (`auto`/`judge`/`human`, most-restrictive-wins, fail-closed to `human`); relaxing a tier is a one-line owner-signed diff, so the file's history is the audit trail of delegation. Plans declare their touch-set; the reconciler enforces containment (actual diff ⊆ declared surface) and demotes a PR that exceeds it back to re-approval. A judge agent deploys classifier-style: shadow mode first (verdict comments, zero authority), with any future authority asymmetric — free to bounce, auto-approve only within the policy file's bounded class — and never judging a plan it authored. Above all of it, unconditional and permanent: **an ADR-bearing issue routes to the owner before any policy lookup runs.** The rule lives in /approve's skill text rather than the policy file precisely so it cannot be relaxed by a config diff; the ladder never reaches the rung where the architecture decides itself.

Skills adapt to headless execution by thin wrappers, not forks: the original SKILL.md remains normative and is read at runtime; a wrapper overrides only the enumerated interaction surface (ask-and-park, end-turn-not-wait, checkout-as-isolation, re-entrancy-first, identity assertion, session sync). Process judgment stays single-sourced.

## Consequences

- The review-flow fragility that motivated this work is fixed at rung 0, before any autonomy exists: thread resolution and hold state become computed, and a stalled obligation is visible as a PR resting in `findings` rather than as a silently wrong flag.
- The owner's control surface is small and explicit: two human gates (`/approve` at Plan→Ready, landing rules at `held`→Done), one policy file, one kill switch, one per-issue label, and the governor variables. Everything else is machinery.
- Issue and PR state stop being inferable only by archaeology; the tick, the judge, and any future tooling read one label.
- New failure modes are accepted knowingly: cron lateness (waves are idempotent, latency-only), spot reclaim mid-job (re-entrant tasks redo work since the last push), subscription-window exhaustion (the pipeline stalls visibly and resumes on the next window). The rejected failure modes — stale claims, asserted flags, orphaned working states — are designed out rather than mitigated.
- Skill text grows: three headless wrappers plus a shared protocol document, a new `/findings` skill, and gate text in `/approve`. All of it rides the self-modification guardrail, so the agent cannot amend its own operating rules without the owner's sign-off.
- Follow-on work this creates: the self-improvement loop (pipeline telemetry → scheduled retrospection → evidence-carrying promotion proposals → before/after evaluation) is deliberately not designed here; it waits until rungs 0–3 produce the exhaust it would feed on.

## Alternatives considered

- **Sub-states under a `refine` umbrella** (`refine:building`, …) — rejected: two vocabularies for one lifecycle, asymmetric for humans and agents; the flat ladder carries the same information in one namespace.
- **Claim labels with heartbeat cleanup** — rejected: asserted liveness goes stale the moment a worker dies, and every cleanup pass re-derives what the runs API already knows authoritatively; a reset-at-tick variant additionally re-dispatches healthy long jobs.
- **A blocking wave barrier held by a runner** — rejected: GitHub Actions has no place for a long-lived waiter; a held runner is a wedge risk and a cost. The computed quiescence predicate yields the same semantics with no waiting process.
- **PAT or `GITHUB_TOKEN` identity** — rejected: `GITHUB_TOKEN` events do not trigger downstream workflows (breaking CI on agent-opened PRs); a PAT blurs agent actions into the owner's identity and is one long-lived broad credential.
- **Forking the skills for CI** — rejected: duplicates the judgment text; the fork drifts from the original and quietly runs stale process. Wrappers keep one soul.
- **An external orchestrator service** (hosted daemon, queue, or bot) — rejected: reinstates the always-on component the design exists to avoid, moves state off GitHub, and adds an operational surface with no compensating capability at this scale.
