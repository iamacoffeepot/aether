# ADR-0129: HTTP server websocket upgrade

- **Status:** Accepted (shipped — HTTP websocket upgrade in `crates/aether-http/src/server/runtime/websocket.rs`)
- **Amended by:** ADR-0132 — the data-phase kinds (`WebSocketMessage`, `WebSocketClose`) carry an explicit `stream_id` and outbound mail routes by it; the causal-chain-root routing this ADR describes for outbound messages is superseded.
- **Date:** 2026-07-03

Extends **ADR-0108** (the `aether.http.server` capability) and **ADR-0128** (response streaming with windowed flow control). ADR-0128 named websocket upgrade as a distinct later increment on its protocol foundation: "adds the `Upgrade` handshake and a bidirectional framed message protocol on the upgraded socket. It composes with the writer thread and credit mechanism but is a distinct surface." This ADR is that increment. Builds on the settlement model of **ADR-0080** / **ADR-0106** and the synchronous-inline mail routing of **ADR-0038**.

## Context

The HTTP server capability serves one request per connection and closes (`Connection: close`, ADR-0108 §5). ADR-0128 adds a response-streaming surface — a handler emits a body incrementally across many mails under a windowed credit protocol, drained to the socket by a per-connection writer thread. That surface is unidirectional: handler produces, peer consumes. A websocket is bidirectional and long-lived — after an HTTP handshake the connection is repurposed to carry framed messages both directions, over minutes, with no HTTP response ever written. It is the shape neither the buffered path nor response streaming reaches.

Three forces shape the answer.

**The upgrade handshake is a fixed protocol.** RFC 6455 §4.2 defines it: the peer sends an HTTP request with `Upgrade: websocket`, `Connection: Upgrade`, `Sec-WebSocket-Version: 13`, and a `Sec-WebSocket-Key`. The server replies `101 Switching Protocols` with `Sec-WebSocket-Accept` = base64(SHA-1(key + `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`)). The GUID, the SHA-1, and the base64 are all mandated — this is not a design choice, it is the wire contract every browser speaks. After the `101` the HTTP framing is gone and both sides speak the RFC 6455 frame format (FIN + opcode + mask bit + 7/16/64-bit length + optional 4-byte masking key + payload).

**Settlement forbids a connection-long chain.** A causal chain is live while it has unbalanced sends or an outstanding hold, and the per-actor trace rings evict with settlement-awareness (ADR-0106, `runtime/trace.rs`). A websocket that pinned one chain open across thousands of messages over minutes would defeat trace-ring eviction and grow every actor's ring toward its ceiling — the same cost ADR-0128 §4 identified for a stream-long hold. So each websocket message, each direction, must be its own short chain that settles as it is handled.

**The v1 I/O regime is thread-per-connection.** ADR-0128 §3 established the per-connection writer thread as the v1 mechanism and named an event-driven I/O loop (non-blocking sockets + readiness polling) as the deferred scale path — "Websocket at scale (thousands of mostly-idle long-lived sockets) is the increment that forces it; the wire kinds and credit protocol are unchanged by that swap, only where blocked writes park." This increment lands in that v1 regime, on the loopback-default bind, with the reader thread and writer thread ADR-0108 and ADR-0128 already spin per connection. The event loop is a recorded precondition for the scale regime, not for this increment (see Consequences).

## Decision

Add **websocket upgrade** to `aether.http.server`: the cap validates an inbound RFC 6455 handshake, lets the handler accept or decline it, and on accept transitions the connection into a bidirectional framed-message mode carried by the reader thread (inbound) and the ADR-0128 writer thread (outbound). Each message is one mail on its own settling chain; outbound backpressure reuses the ADR-0128 credit protocol unchanged.

### 1. The handler decides; the cap owns the protocol

An inbound request carrying `Upgrade: websocket` is dispatched to the handler as an ordinary `HttpServerRequest` — the handler sees the method, path, and headers and applies its own policy (auth, path routing). The cap validates the *protocol* layer before dispatch: a malformed handshake (missing `Sec-WebSocket-Key`, `Sec-WebSocket-Version` ≠ `13`) is answered `426 Upgrade Required` / `400` by the cap itself, never reaching the handler. On a well-formed upgrade request the cap stashes the connection's `Sec-WebSocket-Key` in its per-connection state and dispatches the request. The handler replies one of two kinds:

- `HttpServerResponse` — **decline.** The upgrade is refused and the connection serves that response and closes, exactly as today. A handler unaware of websockets is unchanged.
- `WebSocketAccept` (new) — **accept.** The cap computes `Sec-WebSocket-Accept` from the stashed key, writes the `101 Switching Protocols` head with any handler-supplied subprotocol/headers, and transitions the connection into websocket mode.

Policy lives in the handler; the fixed RFC handshake (key echo, `101` framing) lives in the cap.

### 2. Kind vocabulary — three new kinds, reusing `HttpStreamCredit`

New wire kinds in `crates/aether-capabilities/src/http/kinds.rs` (owned by the server capability per ADR-0121), reusing `HttpHeader`:

- `WebSocketAccept { subprotocol: Option<String>, headers: Vec<HttpHeader> }` — the handler's opt-in reply to an upgrade request (the websocket analog of ADR-0128's `HttpResponseStreamOpen`). Declares an optional negotiated subprotocol and any extra `101` headers; the cap supplies `Upgrade` / `Connection` / `Sec-WebSocket-Accept` itself.
- `WebSocketMessage { stream_id: u64, binary: bool, data: Vec<u8> }` — one complete, de-fragmented application message, **both directions**. Cap → handler on inbound (dispatched as a fresh root, §4); handler → cap on outbound (framed to the peer under credit, §3). `stream_id` names the connection and outbound mail routes by it (ADR-0132; `WebSocketClose` carries it identically); `binary` selects the RFC 6455 opcode (`0x2` binary / `0x1` text); `data` is the reassembled payload.
- `WebSocketClose { code: u16, reason: String }` — the close handshake, **both directions**. Handler → cap initiates a close; cap → handler reports a peer-initiated close. The cap writes/echoes the RFC 6455 close frame and tears the connection down.

Outbound backpressure reuses ADR-0128's `HttpStreamCredit { credit: u32 }` unchanged: outbound `WebSocketMessage`s ride the same per-connection writer-thread bounded channel, and the cap replenishes the handler's send window as writer slots free. Control frames (ping / pong) are **not** surfaced as kinds — the cap owns them (§5).

Correlation reuses the ADR-0108 in-flight table for the handshake dispatch; once upgraded, the connection is keyed by its `ConnId` in per-connection websocket state, not by a held correlation.

### 3. Outbound — the ADR-0128 writer thread and credit, unchanged

An upgraded connection's outbound path is exactly ADR-0128's: a per-connection writer thread fed by a bounded channel is the socket-backpressure sink, and a slow peer blocks the writer thread, never the scheduler. The cap serializes each outbound `WebSocketMessage` / `WebSocketClose` / control frame into an RFC 6455 frame and pushes it onto that channel; the writer thread masks nothing (a server-to-client frame is unmasked per RFC 6455 §5.1) and drains to the socket. As slots free the cap mails `HttpStreamCredit` back to the handler, bounding the handler's in-flight outbound messages by the window. When credit reaches zero the handler — an ordinary actor — pauses until the next credit mail. The window is the ADR-0128 config knob; no new outbound mechanism is introduced.

### 4. Inbound — the reader thread reframed, per-message roots

On upgrade the per-connection reader thread (ADR-0108) is repurposed. Before upgrade it parses one HTTP request then blocks for the response (ADR-0108 `run_reader_loop` phase 3); on upgrade the dispatcher flips a per-connection mode signal and extends the read timeout to a websocket idle deadline (an idle websocket is normal, unlike a slow-loris request), and the reader thread enters an RFC 6455 frame loop: read a frame, unmask the payload (a client-to-server frame is always masked), reassemble continuation frames into one message, and post it. Each complete inbound `WebSocketMessage` is dispatched to the handler via `send_envelope_as_root` — **its own fresh causal chain that settles as the handler finishes it**. No chain spans the connection (§Context, ADR-0106). A peer-initiated close frame posts a `WebSocketClose` to the handler and begins teardown.

Inbound flow control is deliberately *not* in this increment. Inbound messages dispatch as fresh roots into the push-accept-always mail layer (ADR-0038), matching the existing request-dispatch posture — a fast peer can outrun a slow handler's inbox. Read-side backpressure (crediting the socket reader, mirroring ADR-0128's direction) is the streamed-request-bodies increment's mechanism; websocket inbound composes with it when it lands but does not block on it. In the v1 regime — loopback-default bind, a bounded count of live sockets — the unbounded-inbound posture is the same one the request path already carries.

### 5. Control frames and close are cap-owned

Ping / pong are transparent: the cap answers an inbound ping with a pong on the writer thread and may emit periodic pings as an idle keepalive, never surfacing either to the handler. Only application data and close reach the handler. Close is a handshake: either side sends a close frame, the cap echoes one and tears the connection down (reader mode flag flipped, writer thread drained and joined, per-connection websocket state dropped). A handler `WebSocketClose` mail initiates the close; a peer close frame reports `WebSocketClose` to the handler and closes. The existing `unwire` teardown (shutdown flag + socket shutdown + thread join) covers websocket connections unchanged.

### 6. Handshake crypto — hand-rolled SHA-1, workspace base64

`Sec-WebSocket-Accept` needs SHA-1 (RFC 6455 fixed) and base64. `base64` is already a workspace dependency; the cap inherits it (`base64 = { workspace = true }`, runtime-gated). SHA-1 is hand-rolled in the runtime module rather than adding a `sha1` crate — the same instinct as ADR-0108's hand-rolled `http_date` (no date crate for one header). The input is fixed and short (a 24-char key + the 36-char GUID), the algorithm is a fixed ~70 lines, and RFC 6455 §1.3 supplies a worked test vector (`dGhlIHNhbXBsZSBub25jZQ==` → `s3pPLMBiTxaQ9kYGzzhZRbK+xOo=`) that pins the implementation as a tripwire. Both live only under `feature = "runtime"` in `server/runtime.rs`, so the wasm-safe `kinds.rs` half is untouched. The frame codec (parse / serialize RFC 6455 frames, masking, fragmentation reassembly) is likewise hand-rolled — no async websocket crate (tungstenite) is pulled, since those carry an async runtime that does not fit the thread-per-connection model.

## Consequences

- **Positive** — a handler serves a live bidirectional channel: chat, live telemetry, an interactive tool session, the substrate-as-general-application-host story's real-time half. The buffered and response-streaming paths are untouched; a handler that never replies `WebSocketAccept` is unchanged. The wire vocabulary is small (three kinds) and reuses `HttpHeader` and `HttpStreamCredit`.
- **Positive** — settlement stays bounded: each message is its own short chain, so a websocket open for minutes costs the trace ring nothing beyond the messages actually in flight, and the credit signal keeps outbound in-flight bounded and legible in traces.
- **Neutral / cost** — three new wire kinds, a hand-rolled RFC 6455 frame codec and SHA-1, a per-connection websocket mode on the reader thread (extended idle timeout, frame loop), and per-connection websocket state (stashed key during handshake, reassembly buffer, close state). One direct dependency added to `aether-capabilities` (`base64`, already in the workspace). A websocket idle-timeout knob joins `HttpServerConfig`.
- **Negative / risk** — a bidirectional framed protocol with an upgrade handshake and a close handshake is a real state machine (handshake → open → close, with fragmentation reassembly, control-frame interleaving, and peer-disconnect-mid-message paths) the cap must drive correctly. The frame codec is hand-rolled; masking, continuation frames, and the 64-bit length path are the sharp edges, covered by unit tests over the RFC frame examples. A misframed or oversized inbound frame must be answered with a protocol-error close, not a panic — a trust boundary the implementation must pin, since inbound frames are untrusted external input (ADR-0108 §6).
- **Follow-on** — inbound flow control (read-side credit) composes with the streamed-request-bodies increment and is not part of this change. Per-message compression (`permessage-deflate`) is out of scope. At scale — thousands of mostly-idle long-lived websockets — the thread-per-connection model is the wrong shape (one blocked OS thread per idle socket), and the event-driven I/O loop ADR-0128 §3 defers is the refinement that regime forces; the wire kinds and credit protocol here are unchanged by that swap, only where blocked reads and writes park. This increment targets the v1 regime (loopback-default bind, a bounded count of live sockets — a dev tool, a local dashboard, an interactive harness), where thread-per-connection is adequate; the event loop is a recorded precondition for the scale regime, not for this increment.

## Alternatives considered

- **Event-driven I/O loop as a hard precondition for this increment.** Rejected: it forces the ADR-0128 §3 scale refinement (non-blocking sockets, readiness polling, per-connection partial-I/O bookkeeping subsuming both reader and writer threads) before any websocket ships, a large piece of infrastructure the v1 regime — a handful of live sockets on loopback — does not need. ADR-0128 already blessed thread-per-connection as the v1 mechanism and named the event loop as the deferred scale path; the wire vocabulary and credit protocol this ADR pins are unchanged by the eventual swap, so scoping websocket on threads now creates no protocol rework. The event loop lands when connection count demands it, as its own increment.
- **A dedicated upgrade-request kind delivered to the handler.** Rejected: the handler already receives the full `HttpServerRequest` with the `Upgrade` / `Sec-WebSocket-Key` headers, so a separate kind would duplicate the request surface. Detecting the upgrade from the request headers (handler side) and opting in with `WebSocketAccept` reuses the existing dispatch path — the upgrade is just a request the handler answers with a different reply kind.
- **The cap accepts every upgrade automatically (no handler opt-in).** Rejected: whether to upgrade is policy — auth, path, subprotocol negotiation — which lives in the handler, not the cap. The two-reply model (`HttpServerResponse` declines, `WebSocketAccept` accepts) keeps protocol in the cap and policy in the handler, mirroring how ADR-0128 lets the handler choose streaming by its reply kind.
- **One connection-long settlement chain for the websocket session.** Rejected for the same reason ADR-0128 §4 rejected a stream-long hold: it defeats the trace ring's settlement-aware eviction and grows every actor's ring toward its ceiling over a multi-minute session (ADR-0106). Per-message fresh roots keep the trace surface bounded.
- **Pull an async websocket crate (tungstenite).** Rejected: those carry an async runtime and an I/O model that fights the thread-per-connection design; the RFC 6455 frame codec and the handshake are a bounded, testable amount of hand-rolled code (the frame format and a single fixed SHA-1), consistent with the cap's existing hand-rolled `http_date` and `httparse`-only posture.
- **Add a `sha1` crate for the accept-key.** Rejected in favor of a hand-rolled SHA-1: the input is one fixed 60-byte string, the algorithm is fixed, and RFC 6455's own worked test vector pins it as a tripwire — the same call ADR-0108 made hand-rolling `http_date` rather than adding a date crate. `base64` is reused because it is already a workspace dependency; SHA-1 is not, and one fixed hash does not earn a new dependency.
- **Surface ping / pong to the handler.** Rejected: RFC 6455 keepalive is a transport concern with a fixed response (answer a ping with a pong), so the cap owns it transparently and the handler sees only application data and close — a simpler handler contract.
