# ADR-0193: Suppression requests are lane-stated and reviewer-granted

- **Status:** Proposed
- **Date:** 2026-08-14
- **Amended:** 2026-08-26 — §5's mechanism sentence was corrected to the post-ADR-0191 route (`reduce_suppression_disposition`); the decision is unchanged.

## Context

ADR-0181 made `verify.suppress` the eighth verifier identity so that a candidate making another verifier green by construction becomes a forgivable, chargeable, wedgeable failure rather than a lane-killing one. The check behind that identity is `scripts/check-suppressions.py`: it resolves the merge base of `--base` and `--head`, collects every `#[allow(…)]` / `#[expect(…)]` / `#[ignore]` an added line introduces plus every new top-level `.jscpd.json` `ignore` and `package.metadata.cargo-machete.ignored` member, prints each finding as `path:line — token — source`, and exits 1 when it found any.

The scanner already knows how a finding is cleared, and that path belongs to a reviewer rather than to an author. Given `--pull-request` and `--repository`, `trusted_signoff` asks GitHub for the pull request's body, its last editor, and its head oid, and clears the findings only when the body carries exactly one canonical `<!-- aether-suppression-signoff:v1 {…} -->` marker whose payload is exactly `{"base_sha": <merge base>, "head_sha": <head>, "pull_request": <number>}` and whose last editor's login equals the repository owner's. `.github/workflows/ci.yml`'s `New suppressions` job supplies those arguments on the pull-request event, so the repository gate holds both halves of a working mechanism: a refusal, and an owner-stamped grant bound to the exact commits it was granted over.

A bloom lane holds only the first half. `verify_command("verify.suppress")` in `xtask/src/transform/verify/mod.rs` runs the scanner bare — no `--pull-request`, no token, and rightly so, because the mechanical lane is the zero-secret path and no pull request exists at the moment a member verifies. Its `finding_exit_codes: &[1]` reads the scanner's exit 1 as a finding about the candidate, `member_outcome` answers `MemberOutcome::Failed`, and the umbrella reports `verify.suppress` in `failed_verifiers`. A member that legitimately needs an allow the repository's own policy blesses is left with two moves: buy a `Refine` lap that removes it, or write the same read in a form the ban does not enumerate. `clippy.toml` blesses several of those reads in the entry text itself — `std::env::var` names process-level tuning knobs, genuinely external variables, and tests among the cases that may `#[allow]` with a reason — so the lane's refusal fires on writes the policy agrees with, and the member pays for agreement.

Both moves are in the record. `verify.suppress` is the verify refusal the journal carries most often, and #4926 shows where the pressure goes once the loud form is closed: refused a new `#[allow(clippy::disallowed_methods)]`, a lane replaced `env::var("AETHER_HTTP_PORT")` with an `env::vars()` walk in `xtask/src/bloom/mod.rs` — semantically identical, outside the enumerated ban, and named as such in the member's own commit message. The gate caught the greppable form and the ungreppable one shipped. A refusal with no request path beside it selects for exactly that substitution, which is a worse outcome than the suppression it refused, because the next audit of ambient environment reads greps for the disallowed calls and finds nothing.

## Decision

A candidate may **state** a suppression request; only a reviewer **grants** one. The lane's binary refusal gains a third state, the request travels as typed evidence, and every disposition is journaled with its granter.

### 1. A request is stated on the suppression it describes

The request rides the added source line, as a trailing comment on the attribute the scanner finds:

```rust
#[allow(clippy::disallowed_methods)] // aether-suppression-request: operator tooling reading the coordinator's REST bind, not cap config
```

`scripts/check-suppressions.py` already carries what this needs. `collect_added_lines` records each added line's **raw** text, `sanitize_rust` masks comments only in the parallel view used to extract the lint token, and `Suppression` keeps that raw text in its `source` field, which `render` already prints. The scanner therefore reads the marker off the finding it is already reporting, and a request is parsed rather than correlated.

Attaching the request to the line dissolves the binding problem instead of managing it. There is no manifest whose entries must be matched to findings, so there is no multiset to reconcile, no stale entry to expire, and — the question a separate document forces — no behavior to define for a diff that shifts a line number, because a shift moves the request and the suppression together. Widening after the fact is likewise unrepresentable: changing which lint is allowed, or which file the allow sits in, edits the same physical line, which produces a different finding carrying a different request, surfaced fresh to the reviewer. The line number the scanner prints is for reading and is bound to nothing.

The lane learns to write the marker from `xtask/src/transform/construct_instructions.md`, the construct lane's own in-repo instruction source that `CONSTRUCT_INSTRUCTIONS` embeds — the same place the lane learns every other convention it must satisfy.

### 2. `verify.suppress` distinguishes three states

The scanner gains a third terminal beside its finding and its `OperationalError`: exit **3** when it found suppressions and *every one of them* carries a request marker with a non-empty reason. A single unrequested finding among many keeps the whole run at exit 1, so a request cannot smuggle a neighbour through. `--pull-request` retains its meaning and precedence: an owner-stamped marker on the repository path still clears findings to exit 0, requested or not, so `.github/workflows/ci.yml`'s job behaves exactly as it does today.

`VerifyInvocation` states that code the way it states `finding_exit_codes`, and `member_outcome` maps it to `MemberOutcome::Passed`. The member's dispatch therefore proceeds: the umbrella's `umbrella_status` reports `pass`, `failed_verifiers` carries no `VerifyFailure::Suppress`, and ADR-0181's forgiveness arithmetic is untouched because no identity was added and none was removed. The requests themselves ride out on their own presence-driven channel on the lane's `Evidence` record in `xtask/src/transform/mod.rs`, alongside `findings`, `failed_verifiers`, and `environment` — a separate channel for the reason those three are separate: findings are handed to a repair lap as work, and a request handed over as work would be repaired away by the next model that reads it.

### 3. The request is typed, content-addressed evidence

A `SuppressionRequest` value joins `crates/aether-bloomery/src/values/`, carrying the path, the reported line, the lint token, and the reason, and content-addressed like every other durable value. `EvidenceKind` gains a `SuppressionRequest` discriminant, tail-appended past `ReviewAdvisory` exactly as `ReviewAdvisory` was appended past `RepairTriage`, and `reduce_admit_evidence`'s bound-class list admits it through the existing `Fact::AdmitEvidence` door; a request raises no hold and advances no member, so its fold is the plain `Decision::RecordEvidence`.

Beside the journal, the host persists the requests keyed by `(bloom, workpiece)` in the bloomery store, written from `persist_consumed` in `crates/aether-chassis-bloomery/src/bloomery/intake/admit.rs` on the same seam that writes `record_review_findings` and cleared by the same rule that calls `clear_review_findings` — a passing Verify carrying no request clears the row, so the standing set is always what the member's current candidate actually asks for. Both surfaces exist because they answer different questions: the journal answers "what was asked and who answered", and the keyed row answers "what does this member's live candidate need right now", which is what the two reviewer surfaces below render.

### 4. The reviewer sees it where the reviewer already works

**The aggregate review.** The requests standing against the bloom's members are handed to the composition review with the fold it judges, so the critic reads the proposed allow and its stated reason beside the diff that introduces it rather than discovering an `#[allow]` in a hunk with nothing to say about why it is there.

**The landing proposal.** `body_for` in `crates/aether-chassis-bloomery/src/bloomery/reactor/land/runtime/proposal.rs` gains a pending-requests section built the way `waivers_section` is built from `Fact::OperatorAdjudication`: one line per request naming the workpiece, the path, the lint, and the reason, followed by the canonical marker text the reviewer would paste to grant it. The coordinator renders those bytes and never places them. It cannot: `trusted_signoff` accepts a marker only when `editor.login` equals the repository owner's, and a body the coordinator authored and never had edited reports `editor` as null, which fails the check by construction. A grant is therefore an edit by the owner or the delegated reviewing session, on a body the coordinator composed, and the payload's `head_sha` binding means a later push invalidates it and asks for the decision again.

### 5. The grant is journaled by observing it, and a denial has its own door

The coordinator's land reactor already polls its open proposal every pass and merges only on a green gate, which is the pass in which the marker either exists or does not. It reads the same three facts `trusted_signoff` reads: the marker payload, the body's last editor login, and the head oid. On a valid marker it admits a tail-appended `Fact::SuppressionDisposition { bloom, workpiece, disposition }` whose `SuppressionDisposition` value mirrors `Adjudication` field for field in intent — the requests it closes named by digest, granted or denied, the reason, and the operator — with the granter taken from the editor login the check itself trusts. The grant costs the reviewer one act, and "who granted this allow" becomes a journal query.

A denial is the reviewer's other answer, and it needs a door of its own because there is no marker for "no". `POST /blooms/{id}/members/{workpiece}/suppression` sits beside `adjudicate`, `repair`, `hold`, and `release` in `crates/aether-chassis-bloomery/src/api/runtime/blooms.rs`, refuses a blank reason, a blank operator, or an empty request set the way those routes refuse a malformed body, and admits the same fact with the denied disposition.

Both answers land on one reducer arm of their own, `reduce_suppression_disposition` in `crates/aether-bloomery/src/reduce/suppression.rs`. A grant decides nothing about the line — the candidate cleared `verify.suppress` the moment the requests were stated, so the arm produces no effects and answers `Outcome::SuppressionAnswered { reopened: false }`, and the granter's name reaches the record through the admitted fact. A denial re-opens the member on the candidate that carries the refused suppression: `Decision::RevokeResolution` first when the member holds a resolution claim, then a `Refine` re-entry built by `move_effects_with_candidate` against that candidate's own tree and checkout. The lap is charged a repair roll folded into the member's seen set under `VerifyFailure::Suppress`, so a second denial of the same member reads as a repeat rather than a fresh identity, and a member at `StageId::Verify`'s retry budget takes a `Decision::RecordWedge` instead of another lap.

The arm is the member's only re-entry door because nothing else opens one. Under ADR-0191 §4 a reviewed member is immutable, and `reduce_aggregate_review_completed` in `crates/aether-bloomery/src/reduce/review.rs` honours that: a blocking aggregate verdict records its finding with the implicated set as a *label* on it, then repairs the weave through `reweave`, dispatching against no member and revoking no member's claim. There is no member re-entry there for a denial to fold onto, and a denial is not the aggregate reviewer's verdict about the composition anyway — it is a person's answer to a question one member asked.

The denial's reason travels on the journaled fact and into `Snapshot::suppression_dispositions`, not onto the member's findings channel. That channel is written at intake from what a lane's own evidence reported, so a person's words placed there would sit where every reader expects a gate's and would be overwritten by the next verify capture; the repair lap reads the refusal from the journal, which is where the answer lives. A denied request therefore spends the member's retry budget exactly as any other bounced lap does, and the record of the refusal outlives the lap.

### 6. Wire discipline

This reaches the wire-frozen enums under `crates/aether-bloomery/src/reduce/`. `Fact` gains one variant, `Decision` gains its recording variant, `Outcome` gains the admitted and rejected variants that go with them, and `EvidenceKind` gains its class — every one of them **tail-appended**, so no already-journaled row changes meaning, in the discipline every appended variant in `crates/aether-bloomery/src/reduce/event.rs` states for itself.

The pinned fixture moves in the implementing diff. `every_wire_reachable_family_is_represented` in `crates/aether-bloomery/tests/golden_decisions/completeness.rs` fails the moment a family reachable from `Decision` is absent from `representative()`, so the new variants are instantiated there and `GOLDEN_DECISIONS` in `crates/aether-bloomery/tests/golden_decisions/main.rs` is repinned in the same change. `GOLDEN_DECISION_DIGEST` in `crates/aether-bloomery/tests/golden_trace.rs` pins what a scripted bloom *decides*, and a scripted bloom that states no suppression request decides nothing new, so that golden holds unless the implementing diff changes the trace.

## Consequences

- A member needing a policy-blessed allow states it once and continues. The refine lap that removed a correct suppression, and the substitution that hid an identical read behind an unenumerated API, both stop being the only moves available.
- The suppression stays greppable, which is the property #4926's evasion destroyed. A request is an `#[allow]` with a comment on it, so every audit of ambient environment reads, ignored tests, or duplicate-detection carve-outs still finds it by grepping for the attribute.
- "Who asked for what allow, and who granted it" becomes one journal query over `Fact::SuppressionDisposition` instead of an archaeology of pull-request bodies and lane logs.
- ADR-0181's identity, its bit, and its forgiveness arithmetic are untouched. `verify.suppress` still fails on an unrequested suppression, is still forgiven once, still charges a repair roll on a repeat, and still wedges the member with `repeated_verifiers = {verify.suppress}` at budget.
- The honest failure mode is a reviewer who rubber-stamps. The mechanism makes granting cheap — read a line, paste a marker — and cheap approval is approval that gets given without reading. Two things bound the damage and neither eliminates it: the request's reason is the *lane's* words, so a reviewer who reads only the reason is reading the applicant's case for itself rather than the code, and the marker binds `head_sha`, so a stamp cannot ride forward onto work the reviewer never saw. What remains is a genuine transfer of judgment to a person who may not exercise it, and it is the transfer the decision is for.
- A second, smaller residue: between the lane passing a requested suppression and the reviewer answering, the candidate carrying that suppression flows through integration and the composition review. Nothing lands on it — the repository's `New suppressions` job refuses the landing branch until the marker is placed — but a denial arrives after the member has integrated, and re-opening it spends budget the bloom had already banked. Denials are expected to be rare relative to grants precisely because the request states its case in advance; a bloom in which they are not is a bloom whose lane is proposing suppressions it should not be.
- Costs, accepted: a third terminal in the scanner and the branch in `member_outcome` that reads it, one durable table keyed by member, one REST route, four tail-appended wire variants, and a repinned decisions fixture.

## The trust argument

Moving the decision to the reviewer does not weaken ADR-0181's gate, because the gate that keeps a suppression out of the repository is not the one that changes.

Nothing merges to mainline except through a pull request, and every pull request runs the `New suppressions` job, which materializes the scanner from the **event base** rather than from the proposed tree — so a candidate cannot weaken the scanner that judges it — and clears findings only on an owner-edited, commit-bound marker. That job is untouched here. Before this decision, a bloom-authored suppression could reach mainline only with that marker present. After it, the same is true, with the same check, the same trust anchor, and the same binding.

What changes is where the lane stops. Today `verify.suppress` refuses inside the loop, at a point where nobody can grant anything, and the refusal's practical effect is to spend a repair roll or to route the write around the ban. After this decision the lane defers a *stated* suppression to the point where a grant is actually available, and refuses an unstated one exactly as before. The lane never grants; it declines to answer a question it has no standing to answer, and it carries the question forward with the candidate instead of converting it into an unrelated edit.

The residual risk is the reviewer, stated plainly in Consequences: a person who stamps without reading grants what a person who reads would refuse. That risk already exists — it is the risk the owner-marker mechanism has carried since it shipped — and this decision increases the number of times it is exercised rather than changing its nature. The compensating change is that every exercise is now recorded with its granter and its stated reason, which makes a pattern of rubber-stamping a thing the journal can be asked about.

## Alternatives considered

- **An in-lane approval classifier** — a model inside the verify lane that judges whether a proposed allow is policy-blessed and passes it when so. Two independent defects. It is probabilistic in a place with no appeal: a false negative burns a repair roll on a candidate that did nothing wrong, and at the ceiling wedges the member, so the mechanism built to stop paying for correct suppressions starts paying for them nondeterministically. And it judges the wrong object — a classifier reads what the diff *says* about itself, while the question is whether a *process* blesses this write, which is a fact about `clippy.toml`'s carve-outs, the surrounding crate's role, and a policy the diff does not contain. A reviewer reading the request has the process in hand; a judge reading the hunk has the applicant's own account of it.
- **A blanket allow-list of blessed reasons** — enumerate the reason strings the policy already accepts and pass any suppression matching one. It converts the reason from an argument into a password, and the passwords are published in the policy the lane reads, so a lane under repair pressure reaches for the string that passes rather than the one that is true. It also cannot say anything about the *site*: "process-level tuning knob" is a correct reason in an operator binary and a wrong one in a capability's `init`, and a list keyed on the words cannot tell them apart. The narrow version of this — machine-checkable rules over `(crate, path, lint)` — is a real option and remains available later, layered under the request path as a fast accept for cases nobody disputes; it does not remove the need for a request path, because the disputable cases are the ones that stop the lane.
- **Leave the gate as it is** — refuse every new suppression in-lane and let members pay a refine lap or find another way. The refine lap is the priced-and-accepted cost, and where the suppression was genuinely wrong it is the right one. What makes the position untenable is the other outcome, which the record already contains: the lane that cannot get a `#[allow]` writes the `env::vars()` walk instead, and the gate reports green over a change that defeated the lint's enumerability. Holding the line here means choosing an ungreppable evasion over a greppable, reviewed suppression, and the gate's whole purpose is enumerability.
- **A separate request manifest committed beside the diff** — a file listing `(path, line, lint, reason)` entries the scanner matches findings against. It reintroduces every problem attaching the request to the line removes: a line number that shifts under an unrelated repair, a stale entry describing a suppression that is gone, a multiset reconciliation to specify in both directions, and a document a lane can edit independently of the code it describes. It also lands in the repository as permanent noise, whereas a comment on the attribute is the documentation the policy asks for anyway.
- **Route every requested suppression to a parked question** (`EvidenceKind::Question`, ADR-0151) instead of adding a disposition fact. The park machinery already blocks a bloom on an owner decision and releases on a signed answer, which is the right shape — and the wrong granularity. A park stops the member's stage until the answer arrives, so a suppression stated during `Construct` would idle the member through every subsequent stage awaiting a decision that is cheapest to make once, at the end, over the whole composition. It also demands a signed `Statement` per allow, where the existing marker already binds a reviewer's identity to the exact commits.
