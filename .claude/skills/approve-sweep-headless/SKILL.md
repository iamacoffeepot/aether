# /approve-sweep-headless — headless batched approval wrapper

This wraps `/approve`'s [`## Sweep approve`](../approve/SKILL.md#sweep-approve) mode for a headless agent running one-shot on an ephemeral GitHub Actions runner. It carries no process of its own. One dispatch (`task=approve-sweep`, ref constant `all`) processes the whole approve queue: every eligible `phase:plan` issue, each through the full single-issue gate set, in one session — so a wave spends one runner on approval instead of one per issue.

Execute [`## Sweep approve`](../approve/SKILL.md#sweep-approve) verbatim — the REST enumeration, the full per-issue gate checks (freshness, dependency, umbrella integrity, ADR merge, model label), the drop-with-reason accounting, and the per-issue `phase:ready` reconcile — with `../approve/SKILL.md`'s single-issue sections governing each candidate exactly as they govern a single `/approve <n>`. Where the original touches the interaction surface, `../headless/protocol.md` governs. An instruction is overridden if and only if it appears in the Overrides table below, cited by the original's anchor; everything else is the original's, unchanged.

Before any process step, run the protocol's [re-entrancy-first](../headless/protocol.md#re-entrancy-first) guard, adapted to the batch shape: there is no single ref whose label answers "already done", so re-derivation IS the enumeration — a crashed sweep's approved issues rest at `phase:ready` and drop out of the next enumeration; the remainder rest at `phase:plan` and are simply processed again. An empty eligible set is a clean no-op: log it and end the turn. Post no start-of-work comment — the live run is the claim on the whole queue, and per-issue comments appear only where the sweep acts on an issue.

## The authority bound

Identical to [`/approve-headless`'s](../approve-headless/SKILL.md#the-authority-bound), enforced **per issue inside the batch**: this run advances only an issue whose tier resolves to `auto` — by the policy lookup or by an owner-applied `approval:pre-approved` (timeline-actor-verified, per [`### The owner's override`](../approve/SKILL.md#the-owners-override--approvalpre-approved)). Run [`## ADR hard gate`](../approve/SKILL.md#adr-hard-gate) and [`## Approval tier`](../approve/SKILL.md#approval-tier) for each candidate exactly as the original specifies; a `judge`, `human`, ADR-bearing, missing-surface, or unresolvable-tier issue is skipped with a log line and left resting at `phase:plan` for its reader. The dispatcher pre-filters so a sweep is not dispatched when nothing can advance, but the workflow is dispatchable by anything holding `actions: write`, so the bound is enforced here, at the point of each write, rather than trusting the caller.

## Per-issue isolation

One issue's failure never aborts the batch. Every candidate gets an independent outcome — advanced, or a row in [the verdict digest](#the-verdict-digest) (gate failure, non-auto tier, blocked dependency), or skipped entirely (`agent:dont-touch` / parked on another task's question) — and the sweep continues to the next candidate. A candidate that throws mid-check (an API error, a malformed body) becomes a gate-failure digest row carrying the error, never a silent drop. The sweep applies `agent:awaiting-answer` to exactly one issue ever: the digest itself — a work issue is never parked by the sweep.

## Overrides

| Original anchor | Interactive behavior | Headless override |
|-----------------|---------------------|-------------------|
| [`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 1 enumeration | Enumerate every open `phase:plan` issue | Same REST enumeration, minus two exclusions enforced at the point of spend: an issue labeled `agent:dont-touch` (benched by the owner — the tick filters it too, but a control enforced in exactly one workflow is escaped by every other dispatch path) and an issue labeled `agent:awaiting-answer` (parked mid-question by another task; its resume path is its own per-issue dispatch, never a batch). An issue listed on the open digest IS enumerated and fully re-checked — that is how the digest converges (a fixed `auto`-tier issue self-heals and advances, a closed dependency moves its row out of Blocked) — it just never *causes* a dispatch: the tick excludes listed issues from its queue counts, so convergence rides runs the board already warranted |
| [`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 3 "print the approve plan and wait for confirmation" | Hold the whole batch behind one operator confirmation | Split by tier. For the **auto set**: dispatch-as-authorization — the tick's pre-filter plus [the authority bound](#the-authority-bound) above are the confirmation (a headless sweep only ever auto-advances what the policy or the owner's own label already cleared), so print the plan — advanced / skipped-with-tier / parked-with-reason — to the run log and `$GITHUB_STEP_SUMMARY` and proceed without waiting. For the **non-auto remainder**: the confirmation is displaced onto GitHub as [the verdict digest](#the-verdict-digest) — the same plan table, posted as a machine-filed issue the owner answers with one reply |
| [`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 2 drop-with-reason (a candidate failing the [gate checks](../approve/SKILL.md#gate-checks), the [freshness gate](../approve/SKILL.md#freshness-gate), or the [dependency gate](../approve/SKILL.md#dependency-gate)) | Drop the issue from the batch and list the reason in the plan for the operator | A **Gate failures** row in [the verdict digest](#the-verdict-digest) — reason plus a suggested remedy — and a [breadcrumb comment](#the-verdict-digest) on the issue itself. Never a per-issue park: the digest is the one reply surface, and parking a work issue would both multiply the owner's reply obligations and hide the issue from the next sweep behind its `agent:awaiting-answer` exclusion |
| [`## Approval tier`](../approve/SKILL.md#approval-tier) `judge` / `human` routing, and [`## ADR hard gate`](../approve/SKILL.md#adr-hard-gate) | The owner or judge reads the issue | [end-turn-not-wait](../headless/protocol.md#end-turn-not-wait) per issue — never auto-advance it, post no comment on the issue itself (a deliberate divergence from `/approve-headless`, which comments the resolved tier on its one dispatched issue: a sweep re-visits the whole plan board every wave, so a per-visit comment would repost the same verdict on the same resting issues tick after tick). The issue's owner touchpoint is its row in [the verdict digest](#the-verdict-digest); the run summary carries the tier lines |
| [`## Actions on pass`](../approve/SKILL.md#actions-on-pass) step 3 "Print a summary to the user" | Print the `✓ #N approved` summary to the operator's terminal | [end-turn-not-wait](../headless/protocol.md#end-turn-not-wait) — post the summary as a comment on each advanced issue (the same per-issue record `/approve-headless` leaves), and end the turn after the batch completes; dispatch nothing |
| [`## Freshness gate`](../approve/SKILL.md#freshness-gate) Tier A `git fetch origin main` and the `git log`/`git cat-file` reads | Run against the operator's local clone | [checkout-as-isolation](../headless/protocol.md#checkout-as-isolation) — the runner's `$GITHUB_WORKSPACE` checkout is the clone, on the default branch with full history; run the gate unchanged, once per candidate. Cut no branch and no worktree; `/approve` writes no code |

## The verdict digest

The non-auto remainder's one owner touchpoint (#3190): the interactive sweep holds its batch behind a terminal confirmation, and headless that confirmation becomes one machine-filed issue the owner answers with one reply — from GitHub or straight from the notification email (reply-by-email posts back onto the thread, which is what re-dispatches this sweep). Every branch below is re-derived from board state; no branch needs a stored session. Held rows rest until observably changed: once a row is surfaced, the digest lane refiles it only on a **reply-actionable change** to that row — a label added or removed, its `## Depends on` target closing, `origin/main` moving past the paths that caused its freshness drift, or its body edited — so a hold sticks and a remainder that is entirely held-and-unchanged spawns no new digest and no repeat breadcrumbs (#3206).

After the auto lane completes, run the digest lane in this order:

1. **Read an answered digest.** Enumerate open `agent:digest` issues (`gh api 'repos/iamacoffeepot/aether/issues?labels=agent:digest&state=open'` — REST, like every other read here). The verdict is the **latest owner-authored comment** postdating the digest's most recent convergence (the render its body marker's run= names) — later non-owner comments never mask it: a chat turn, a lint bot, or any machine reply arriving after the owner's word changes nothing (#3198's live failure was exactly this masking). Authenticate by comment author — the same trust boundary the `approval:pre-approved` timeline-actor check encodes: only the owner's word waives a tier. Interpret the reply — free-form is expected ("approve all", "approve #3191 and #3195, hold the rest", "dismiss") — and **echo the interpretation** in the outcome comment so a misreading is visible and correctable rather than silent. The approvable set is the intersection of: issues listed in *that digest's* table, still open at `phase:plan` and still eligible on re-enumeration, and not ADR-bearing. For each, run the full single-issue [gate checks](../approve/SKILL.md#gate-checks) — the owner's verdict waives the **tier** (exactly the `approval:pre-approved` semantics: who approves, never whether the issue is approvable) — then apply [Actions on pass](../approve/SKILL.md#actions-on-pass). The verdict may also direct a **mechanical fix, labels only** — "add model:sonnet to #3145 and approve" applies the label and re-runs the gates, which now pass on their own merits; a fix is never a bypass, and a body-level fix (a missing section, a malformed umbrella) is out of reach — reply-direct those to `/bounce`, because the sweep never edits an issue body. Post one outcome comment on the digest (approved / fixed-and-approved / no-longer-eligible / held-by-your-reply, plus the echoed interpretation) and **close the digest issue, removing `agent:awaiting-answer` in the same breath** — closed is its terminal state, and a closed ticket must not keep wearing an awaiting label: every consumer today filters on `state=open`, but the bookkeeping should be true without that filter (#3201). The outcome comment also carries a **ledger marker** — `<!-- aether-agent:held-ledger digest=<n> -->` followed by one per-row fingerprint line (the same `#N labels=<hash> depends=<none|#M:open|#M:closed> surface=<sha|none> body=<hash>` shape branch 3 writes) — restating the baseline of every row this cycle leaves non-advanced, read from the **closing digest's own marker union** (branch 3's held-ledger block) with the entries for rows that advanced or closed pruned out. This comment is the persistence hand-off downstream of the marker: the next branch 3 reads it as the baseline for its new-or-changed partition, so a still-held row keeps its baseline and keeps resting across the close (#3206). A "dismiss"-shaped reply closes it the same way — label off, no approvals. An ambiguous reply re-asks on the digest issue, re-applies `agent:awaiting-answer`, and ends the turn — never guess an approval.
2. **Converge an unanswered digest.** An open digest with no owner reply is still the one reply surface — every run maps to the *same* digest, so re-render it to the current board rather than filing a sibling or letting it rot. First apply the [actionability gate](#the-verdict-digest) to the re-checked set: if it has become **entirely self-healing** — every remaining row a **Blocked — self-healing** row (the rest advanced, closed, or unblocked), with nothing reply-actionable left — close the digest exactly as an answered one closes (post the outcome comment carrying its ledger marker, remove `agent:awaiting-answer`, do not re-park), since there is no longer anything the owner is owed a reply on (#3206). Otherwise regenerate the body wholesale from this run's re-check — the marker with a refreshed `issues=` list and this run's `run=` URL and its adjacent **held-ledger block** rewritten to the current held union (the carried-forward baselines ∪ the current fingerprints of any newly-held rows), the @owner mention, the three-group table — and refresh the ticket-summary title's counts, via a REST PATCH (`gh api -X PATCH repos/…/issues/<digest> -F body=@<file> -f title="…"` — capital `-F` for the body file, per the filing step's command-shape note). A newly listed issue gets its [breadcrumb](#the-verdict-digest); a row whose issue advanced, closed, or unblocked simply renders in its new group or drops out. Wholesale regeneration is the computed-state move — the digest is a projection of the board, never an append-log. Around the re-render, gate a notify-comment on the ask *growing* (#3225): a body PATCH is silent — GitHub sends nothing on a body edit and the already-present @owner mention does not re-notify because it is not new — so a convergence that *adds* a reply-actionable row would otherwise silently grow the digest's ask (the live 2026-07-12 miss folded #3110's fresh awaiting-verdict row into a blocked-only ticket, caught only by a chance browse). Before the PATCH, capture the open digest's **pre-render reply-actionable set** — the `(issue, group)` pairs rendered under the reply-actionable groups (**Awaiting your verdict**, **Gate failures**, **Blocked — needs you**) in the *current* body; after this run's re-check classification, compute the **post-convergence reply-actionable set** the same way over the groups this run will render. When the post set holds any `(issue, group)` pair absent from the pre set — a newly-carried ask — post exactly **one** one-line comment on the digest naming each addition (the issue number, its new group, and, for a gate failure, the one-clause remedy — e.g. `converged: now awaiting your verdict on #3110 (was blocked)` / `converged: new gate failure on #3145 — add model:sonnet`), over REST (`gh api -X POST repos/…/issues/<digest>/comments -F body=@<file>`, body written to a file first so backticks/`$` aren't shell-expanded); when the post set adds nothing, post no comment. The body PATCH is unchanged and stays the canonical render — the comment is purely the notification GitHub won't send. The gate is idempotent by the `(issue, group)` unit: a row already carried in a group is in the pre set on the next convergence, so a re-dispatch that changes nothing re-adds nothing and stays silent, and a row *leaving* a reply-actionable group (advanced, closed, or fallen to **Blocked — self-healing**) is a removal, never an addition, and stays silent by construction — a count-only, re-order, or self-healing/blocked refresh stays silent as today, and only a change to the ask is audible. One open digest at a time, always current as of the last sweep run; the tick's nudge machinery re-pings it on `AGENT_NUDGE_DAYS`. (Between runs it can drift — a dependency closing does not trigger a sweep — which is safe because the verdict path re-checks eligibility and gates at read time; the digest is the menu, the verdict run is the authority.)
3. **File a new digest.** No open digest, and the sweep's non-advanced remainder is non-empty — every plan issue it did not flip to `phase:ready`, whatever the reason: a non-auto tier, a gate failure (any tier, `auto` included), or a blocked dependency — excluding `agent:dont-touch` and issues parked on another task's question.

   Before filing, gate on a real, reply-actionable change so a held-and-unchanged remainder rests instead of re-spamming (#3206). Locate the most recently closed `agent:digest` issue (`gh api 'repos/iamacoffeepot/aether/issues?labels=agent:digest&state=closed&sort=updated&direction=desc&per_page=1'`) and parse the **ledger marker** in its outcome comment (branch 1's `<!-- aether-agent:held-ledger … -->`); with no closed digest yet, treat every remainder row as new. Recompute each remainder row's **fingerprint** over the four observable-change dimensions — the issue's sorted non-`phase:` label set (hashed), its `## Depends on` target's open/closed state (when it has one), the `origin/main` sha captured for a **freshness-drift** row scoped to its declared-surface paths (a later sweep detects drift by `git diff --name-only <baseline-sha> origin/main -- <paths>` being non-empty, never by comparing shas directly), and a hash of the issue body — and partition the remainder into **new-or-changed** (no baseline in the ledger, or baseline ≠ current) vs. **unchanged** (baseline == current). Independently classify each row as **reply-actionable** — an *Awaiting your verdict* row (gate-clean `judge`/`human`), a directable *Gate failure* (labels-only fixable or `/bounce` fodder), or a *Blocked — needs you* row (blocked on an `agent:dont-touch` dependency, or inside a dependency cycle — detected by an iterative visited-set walk of the `## Depends on` graph, bounded by the open-issue set, never recursion) — or **self-healing** (a *Blocked — self-healing* row: an ordinary open dependency, owed no reply). File **only when the remainder holds ≥1 row that is both reply-actionable and new-or-changed**; the human-facing table then shows the new-or-changed rows (Blocked split into its two subgroups). When the gate does not clear, log `N held/self-healing row(s) unchanged or unactionable since digest #M — resting, no digest filed` to the run summary and end the turn: no issue filed, no park, no breadcrumbs posted — the held rows carry on the run summary and their existing breadcrumbs alone.

   Otherwise file **one** new issue — the ticket the sweep runs report into and the owner directs from. Title it conventionally with the counts as the subject: `chore(ci): approve digest — 2 awaiting verdict · 2 gate failures · 1 blocked` (the repo's `{type}({scope}): <subject>` shape, subject lowercase — consistency is the point; the title lint exempts `agent:digest` so no `type:chore` label gets auto-applied, but the convention holds by this text); labels `agent:digest` + `agent:awaiting-answer`, deliberately **no `type:*` label** (that absence plus the digest label keeps the tick's scope arm away — the `alert` invisibility contract). The body carries, in order:
   - the park marker `<!-- aether-agent:awaiting-answer task=approve-sweep ref=all issues=<csv of listed numbers> run=<run-url> -->` — no `session=` (the verdict run re-derives everything from the board); `issues=` is load-bearing: the tick parses it to exclude listed issues from its queue counts, which is what stops a gate-failed `auto` issue from re-dispatching a useless sweep on every completion-chain tick;
   - adjacent to it, an invisible **held-ledger block** `<!-- aether-agent:held-ledger …one line per still-held row… -->`, each line the fingerprint `#N labels=<hash> depends=<none|#M:open|#M:closed> surface=<sha|none> body=<hash>`. It carries the **full held-fingerprint union** — the carried-forward baselines for every still-held-but-unshown *unchanged* row (read from the closed digest's ledger the filing gate just parsed) plus the freshly-captured current fingerprints for the *new-or-changed* rows this digest shows — so a row that never surfaces in the human table still carries its baseline forward, and a later sibling waking a fresh digest cannot lose a quiet row's resting baseline. The block is machine-only and invisible to the three-group table; it is the persistence point the next branch 1 close reads from. Every fingerprint is recomputed from GitHub-observable facts each run — computed state, never a separately-mutated flag;
   - an @owner mention;
   - the verdict table in three groups, so one glance separates decisions from defects from waits: **Awaiting your verdict** (gate-clean `judge`/`human` rows — number, title, tier and the rule behind it, the judge's shadow-verdict link when one exists; reply-approvable), **Gate failures** (number, title, the failing gate and reason, and a suggested remedy — reply-directable per branch 1's labels-only bound, or `/bounce` fodder when the fix is body-level), **Blocked**, split into two subgroups so "waiting on you" and "waiting on the pipeline" stop reading identically (#3206): **Blocked — needs you** (blocked on an `agent:dont-touch` dependency or inside a dependency cycle — neither self-heals through the pipeline, so the row is reply-actionable and names what only the owner can unblock) and **Blocked — self-healing** (an ordinary open dependency — informational, no reply owed: the row names the blocker, and the issue re-enters the pool when its dependency closes and this digest is gone). Every ADR-bearing row, whatever its group, is explicitly marked **not reply-approvable** (the [ADR hard gate](../approve/SKILL.md#adr-hard-gate) is unconditional; those rows are visibility only, approved by the owner running `/approve` himself);
   - the reply instructions: approve or direct in any phrasing, or "dismiss" to close without approving.

   Command shape matters here: write the body to a file first and file the issue over REST with **`-F body=@<file>`** — capital `-F` is what expands the `@file` reference; lowercase `-f` sends the literal string `@/tmp/…` as the body, which is exactly how the first live digest shipped broken (#3196). The title and `labels[]` fields ride `-f` as plain strings. Same rule as the protocol's park comment, restated because it bit.

   Then leave a **breadcrumb on every listed issue** — the single-surface rule cuts replies down to one, not visibility: each issue's own timeline must say what state it is in without a trip through the Actions log. Post one comment per listed issue carrying the marker `<!-- aether-digest-ref digest=<digest-number> -->`, that issue's own row in plain language (its gate failure and remedy, its tier, or its blocker), and the pointer: *replies belong on digest #<n>, not here — this comment asks nothing of you.* No label rides it. Dedupe by the marker: a comment carrying the current digest's number already present means skip; a later digest listing the same issue posts a fresh breadcrumb pointing at the new number.

The digest's lifecycle is computed state: open = awaiting the verdict, closed = done. Nothing else stores digest progress, and a crashed run between filing and answering changes nothing — the issue rests open, the nudge pings it, the answered-or-stale branch above handles whatever the next dispatch finds.

**Not overridden — `--skip-adr`.** Sweep mode already refuses it ([`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 2) and no dispatch can carry one; an unmerged-ADR candidate parks like any other gate failure, to be approved singly by the owner if the override is intended.

Everything the table does not cite — the gate checks themselves, the freshness and dependency and umbrella-integrity logic, the ADR merge gate, the per-issue tier resolution, the `phase:ready` label-reconcile mechanics, the idempotent re-run, the side-findings hands-off rule, and everything under [`## What /approve does NOT do`](../approve/SKILL.md#what-approve-does-not-do) (it dispatches no implementation, edits no issue body, and never edits `.github/approval-policy.yml`) — is `/approve`'s, verbatim.
