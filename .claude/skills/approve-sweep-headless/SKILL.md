# /approve-sweep-headless — headless batched approval wrapper

This wraps `/approve`'s [`## Sweep approve`](../approve/SKILL.md#sweep-approve) mode for a headless agent running one-shot on an ephemeral GitHub Actions runner. It carries no process of its own. One dispatch (`task=approve-sweep`, ref constant `all`) processes the whole approve queue: every eligible `phase:plan` issue, each through the full single-issue gate set, in one session — so a wave spends one runner on approval instead of one per issue.

Execute [`## Sweep approve`](../approve/SKILL.md#sweep-approve) verbatim — the REST enumeration, the full per-issue gate checks (freshness, dependency, umbrella integrity, ADR merge, model label), the drop-with-reason accounting, and the per-issue `phase:ready` reconcile — with `../approve/SKILL.md`'s single-issue sections governing each candidate exactly as they govern a single `/approve <n>`. Where the original touches the interaction surface, `../headless/protocol.md` governs. An instruction is overridden if and only if it appears in the Overrides table below, cited by the original's anchor; everything else is the original's, unchanged.

Before any process step, run the protocol's [re-entrancy-first](../headless/protocol.md#re-entrancy-first) guard, adapted to the batch shape: there is no single ref whose label answers "already done", so re-derivation IS the enumeration — a crashed sweep's approved issues rest at `phase:ready` and drop out of the next enumeration; the remainder rest at `phase:plan` and are simply processed again. An empty eligible set is a clean no-op: log it and end the turn. Post no start-of-work comment — the live run is the claim on the whole queue, and per-issue comments appear only where the sweep acts on an issue.

## The authority bound

Identical to [`/approve-headless`'s](../approve-headless/SKILL.md#the-authority-bound), enforced **per issue inside the batch**: this run advances only an issue whose tier resolves to `auto` — by the policy lookup or by an owner-applied `approval:pre-approved` (timeline-actor-verified, per [`### The owner's override`](../approve/SKILL.md#the-owners-override--approvalpre-approved)). Run [`## ADR hard gate`](../approve/SKILL.md#adr-hard-gate) and [`## Approval tier`](../approve/SKILL.md#approval-tier) for each candidate exactly as the original specifies; a `judge`, `human`, ADR-bearing, missing-surface, or unresolvable-tier issue is never advanced here — [Per-issue asks](#per-issue-asks) posts a per-issue ask-and-park on the reply-actionable ones and rests the rest at `phase:plan`. The dispatcher pre-filters so a sweep is not dispatched when nothing can advance, but the workflow is dispatchable by anything holding `actions: write`, so the bound is enforced here, at the point of each write, rather than trusting the caller.

## Per-issue isolation

One issue's failure never aborts the batch. Every candidate gets an independent outcome — advanced, or a per-issue [ask-and-park](#per-issue-asks) (a reply-actionable gate failure, non-auto tier, or blocked-needs-you dependency), or rested at `phase:plan` with a run-summary line (a self-healing or ADR-bearing candidate), or skipped entirely (`agent:dont-touch` / already parked on another task's question) — and the sweep continues to the next candidate. A candidate that throws mid-check (an API error, a malformed body) becomes a reply-actionable park carrying the error, never a silent drop. The sweep parks each reply-actionable issue on its own timeline; convergence is the `agent:awaiting-answer` label it applies, which drops the issue from the next enumeration (see [Per-issue asks](#per-issue-asks)).

## Overrides

| Original anchor | Interactive behavior | Headless override |
|-----------------|---------------------|-------------------|
| [`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 1 enumeration | Enumerate every open `phase:plan` issue | Same REST enumeration, minus two exclusions enforced at the point of spend: an issue labeled `agent:dont-touch` (benched by the owner — the tick filters it too, but a control enforced in exactly one workflow is escaped by every other dispatch path) and an issue labeled `agent:awaiting-answer` (parked mid-question; its resume path is its own per-issue dispatch, never a batch). That second exclusion is what makes a per-issue ask converge: once the sweep parks a reply-actionable candidate ([Per-issue asks](#per-issue-asks)), the `agent:awaiting-answer` label drops it from every later enumeration, so an unchanged ask is never re-enumerated and never re-asked — convergence is the label, not a ledger. The owner's reply clears the label and returns the issue to enumeration if it is still non-advanced |
| [`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 3 "print the approve plan and wait for confirmation" | Hold the whole batch behind one operator confirmation | Split by tier. For the **auto set**: dispatch-as-authorization — the tick's pre-filter plus [the authority bound](#the-authority-bound) above are the confirmation (a headless sweep only ever auto-advances what the policy or the owner's own label already cleared), so print the plan — advanced / skipped-with-tier / parked-with-reason — to the run log and `$GITHUB_STEP_SUMMARY` and proceed without waiting. For the **non-auto remainder**: the confirmation is displaced onto GitHub per issue — each reply-actionable candidate gets its own [ask-and-park](#per-issue-asks) (a marker comment plus `agent:awaiting-answer`) on the issue it concerns, and each self-healing or ADR-bearing candidate rests at `phase:plan` with a run-summary line only |
| [`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 2 drop-with-reason (a candidate failing the [gate checks](../approve/SKILL.md#gate-checks), the [freshness gate](../approve/SKILL.md#freshness-gate), or the [dependency gate](../approve/SKILL.md#dependency-gate)) | Drop the issue from the batch and list the reason in the plan for the operator | A per-issue [ask-and-park](#per-issue-asks) on the issue itself when the failure is reply-actionable — the marker comment carries the failing gate and a suggested remedy, and `agent:awaiting-answer` both records the ask and, by dropping the issue from the next enumeration, converges it (a fixed gate re-runs only after the owner's reply re-dispatches the single-issue path). A self-healing candidate — an ordinary open dependency, owed no reply — gets a run-summary line only and rests at `phase:plan` |
| [`## Approval tier`](../approve/SKILL.md#approval-tier) `judge` / `human` routing, and [`## ADR hard gate`](../approve/SKILL.md#adr-hard-gate) | The owner or judge reads the issue | [end-turn-not-wait](../headless/protocol.md#end-turn-not-wait) per issue — never auto-advance it. A reply-actionable tier (gate-clean `judge` / `human`) gets a per-issue [ask-and-park](#per-issue-asks) on its own timeline; the `agent:awaiting-answer` label then drops the issue from every later enumeration, so the sweep never re-visits it and cannot repost the same verdict tick after tick (the reposting the old central-ticket design had to route around). An ADR-bearing issue is never reply-approvable — it rests at `phase:plan` with a run-summary line for the owner's own `/approve` run, no park. The run summary carries the tier lines |
| [`## Actions on pass`](../approve/SKILL.md#actions-on-pass) step 3 "Print a summary to the user" | Print the `✓ #N approved` summary to the operator's terminal | [end-turn-not-wait](../headless/protocol.md#end-turn-not-wait) — post the summary as a comment on each advanced issue (the same per-issue record `/approve-headless` leaves), and end the turn after the batch completes; dispatch nothing |
| [`## Freshness gate`](../approve/SKILL.md#freshness-gate) Tier A `git fetch origin main` and the `git log`/`git cat-file` reads | Run against the operator's local clone | [checkout-as-isolation](../headless/protocol.md#checkout-as-isolation) — the runner's `$GITHUB_WORKSPACE` checkout is the clone, on the default branch with full history; run the gate unchanged, once per candidate. Cut no branch and no worktree; `/approve` writes no code |

## Per-issue asks

The non-auto remainder's owner touchpoint (#3316, retiring the central verdict ticket #3190): rather than one shared machine ticket, each issue the sweep cannot advance carries its own ask on its own timeline, and a read-only local tool (`scripts/status-sweep.sh`) aggregates the board-wide "what is waiting on me" view on demand. **Convergence is the label, not a ledger:** the sweep's [step-1 enumeration](#overrides) already excludes `agent:awaiting-answer` issues, so once a reply-actionable candidate is parked it drops out of every later enumeration and cannot be re-asked — an unchanged ask is silent by construction. No fingerprint block, actionability gate, or notify-on-growth comment is needed; the label the board already carries does the held-ledger's whole job (#3206/#3225 delete with the ticket).

After the auto lane completes, walk the non-advanced remainder — every `phase:plan` issue this run did not flip to `phase:ready`, whatever the reason (a non-auto tier, a gate failure of any tier, or a blocked dependency), excluding `agent:dont-touch` and issues already parked on another task's question. Classify each exactly as the retired central ticket classified its rows:

- **Reply-actionable** — an issue the owner can resolve with a reply or a label:
  - an **awaiting-verdict** row: gate-clean, tier `judge` or `human`, and not ADR-bearing — the owner (or the judge) reads it and approves;
  - a **gate failure** the owner can direct: labels-only fixable (e.g. "add `model:sonnet`") or `/bounce` fodder when the fix is body-level (the sweep never edits an issue body);
  - a **blocked — needs you** row: blocked on an `agent:dont-touch` dependency, or inside a dependency cycle — detected by an iterative visited-set walk of the `## Depends on` graph, bounded by the open-issue set, never recursion — neither self-heals through the pipeline.
- **Not reply-actionable** — owed no ask:
  - a **self-healing** row: an ordinary open dependency; the issue re-enters the pool when its dependency closes;
  - an **ADR-bearing** row: the [ADR hard gate](../approve/SKILL.md#adr-hard-gate) is unconditional, so it is never reply-approvable — the owner approves it by running `/approve` himself once the ADR is settled.

For each **reply-actionable** candidate, post the protocol [ask-and-park](../headless/protocol.md#ask-and-park): write the pure-prose question comment carrying the load-bearing "why" first (the failing gate and its one-clause remedy, the resolved tier and the rule behind it, or the blocker), then the owner's options (approve / direct a labels-only fix / `/bounce`), and apply `agent:awaiting-answer` + `agent:park:approve` over the same REST `…/labels` endpoint the phase reconcile uses — the label pair, not a free-text marker, is what routes the owner's reply back to a single-issue `/approve` (#3336). The approve park re-derives the gate context from the board rather than resuming a stored session, exactly as the protocol names. This is the same per-issue park `/approve-headless` already writes for its single dispatched issue and the same shape the sweep's gate-failure parks already carry. No dedupe logic is needed: an issue already wearing `agent:awaiting-answer` from a prior sweep is dropped by the step-1 enumeration and never reaches this lane, so a re-post is structurally impossible — that exclusion *is* the convergence.

Every **not-reply-actionable** candidate gets a run-summary line only — the issue rests at `phase:plan`, nothing is written to its timeline, and it re-enters the pool when its blocker clears (a self-healing dependency) or when the owner acts (ADR-bearing). Log the whole classification — advanced / parked-with-reason / resting-with-reason — to the run log and `$GITHUB_STEP_SUMMARY`.

**The owner's disposition reuses existing verbs.** To approve a parked ask the owner (or an in-session Claude working from `scripts/status-sweep.sh`) applies `approval:pre-approved` — the owner-authored per-issue tier override the tick already honors, timeline-actor-verified per [`### The owner's override`](../approve/SKILL.md#the-owners-override--approvalpre-approved) — or replies "approve" on the issue, which `agent-chat` re-dispatches as a single-issue `work-approve-<n>` run down the `/approve-headless` path that re-checks the gates and flips the label on their own merits; the owner's word waives the **tier**, never the gate checks (exactly the `approval:pre-approved` semantics: who approves, never whether the issue is approvable). A defect is dispositioned with `/bounce`. Either way the reply clears `agent:awaiting-answer`, returning the issue to the sweep's enumeration if it is still non-advanced. No central verdict ticket is ever filed again; the board-wide aggregation its table once gave is now `scripts/status-sweep.sh`, computed on demand rather than maintained as a ticket.

**Not overridden — `--skip-adr`.** Sweep mode already refuses it ([`## Sweep approve`](../approve/SKILL.md#sweep-approve) step 2) and no dispatch can carry one; an unmerged-ADR candidate parks like any other gate failure, to be approved singly by the owner if the override is intended.

Everything the table does not cite — the gate checks themselves, the freshness and dependency and umbrella-integrity logic, the ADR merge gate, the per-issue tier resolution, the `phase:ready` label-reconcile mechanics, the idempotent re-run, the side-findings hands-off rule, and everything under [`## What /approve does NOT do`](../approve/SKILL.md#what-approve-does-not-do) (it dispatches no implementation, edits no issue body, and never edits `.github/approval-policy.yml`) — is `/approve`'s, verbatim.
